- If a Terraform operation is interrupted (e.g., the process crashes or loses network connectivity) while holding a state lock, the lock may not be released automatically.

`terraform force-unlock <LOCK_ID>` manually releases the lock.

### Why remote state file:

- By default, resource attributes — including some sensitive values — are stored in plaintext inside the state file, which is a real security risk.
- Mitigations include:
  - Using a remote backend with encryption at rest.
  - Tightly restricting access to the backend via IAM policies.
  - For secrets used inside configuration, fetching them dynamically from a secrets manager. The values may still land in state, but they never need to be stored in source code.
- Marking variables with `sensitive = true` prevents their values from being echoed in CLI output and logs.

- If state manipulation is genuinely required, use the dedicated `terraform state` subcommands or `terraform import`, which perform the operations safely.

### DO Hands-on — Common causes of drift:

- Manual changes via the cloud console, often due to urgent hotfixes.
- Changes made by other automated tools that are not managed by Terraform.
- Failed or partially completed `terraform apply` runs.

- Drift is detected by running:

```bash
terraform plan
````

 - If Terraform proposes changes even though your configuration hasn't changed, the real infrastructure may have drifted from the recorded state.

 Remediation options:

 - Run `terraform apply` to revert the infrastructure back to what the code describes.
- Update the Terraform code to match the manual change.

 You can use:

```
terraform plan -refresh-only
```

- This updates the state to match reality without proposing infrastructure changes, allowing you to inspect drift before deciding how to act.

- lifecycle tells Terraform how to behave when creating, changing, replacing, or destroying a resource.
- Terraform's normal lifecycle is essentially create, update when possible, or destroy-and-recreate when an in-place update isn't possible.  lifecycle lets you change that behavior.

2. The lifecycle block
It looks like this:
```tf
resource "aws_instance" "web" {

  ami           = "ami-111111"
  instance_type = "t3.micro"

  lifecycle {
    # lifecycle rules here
  }
}

like do not re-run entire terraform just coz I changed tags:
lifecycle {
  ignore_changes = [
    tags
  ]
}

```
The important rules you'll encounter are:
```
lifecycle
│
├── create_before_destroy
├── prevent_destroy
├── ignore_changes
├── replace_triggered_by
├── precondition
├── postcondition
└── destroy
```
The current Terraform documentation also includes action_trigger, which is available for invoking actions around lifecycle events. 

- The `removed` block lets you declare that Terraform should stop managing a resource — removing it from state — without destroying the underlying infrastructure:

```
removed {
  from = aws_instance.legacy

  lifecycle {
    destroy = false
  }
}
```

## lifecycle
Suppose you want:

"Replace my EC2 whenever this variable changes."

You might try:

```tf
resource "aws_instance" "web" {

  lifecycle {
    replace_triggered_by = [
      var.version
    ]
  }
}
```

But replace_triggered_by works with managed resource references, not ordinary variables. 


That's where terraform_data comes in.
```tf
variable "app_version" {
  default = "v1"
}

resource "terraform_data" "app_version" {
  input = var.app_version
}
```

Then:

```tf
resource "aws_instance" "web" {

  lifecycle {
    replace_triggered_by = [
      terraform_data.app_version
    ]
  }
}
```
Now you have:
```
variable
   │
   │ v1 → v2
   ▼
terraform_data
   │
   │ changes
   ▼
aws_instance
   │
   ▼
REPLACE
```
- This is one of the main reasons terraform_data is useful with lifecycle rules. HashiCorp explicitly documents this pattern

## Why lock versions
- Without pinning, a future terraform init could pull a new, potentially incompatible module or provider version, causing unexpected errors or breaking changes.
- You pin a module version with the version argument on a module block (e.g., version = "~> 1.2"), and pin provider versions in the required_providers block inside terraform {}.
```txt
= (or no operator): an exact version.
!=: excludes an exact version.
>, >=, <, <=: comparisons.
~> ("pessimistic constraint"): allows only the rightmost version component to increment — e.g., ~> 1.2 allows 1.2.x but not 1.3.0; ~> 1.2.0 allows only patch-level updates within 1.2.x.
```
#### .terraform.lock.hcl file?
The dependency lock file, generated by terraform init and typically committed to version control, records the exact provider versions (and their checksums) selected for a configuration.
It ensures every team member and CI run uses identical provider versions until someone deliberately runs terraform init -upgrade, preventing silent drift caused by different provider builds across machines.
#### Count vs for each
- **`count`** → Use when you know **how many** identical resources you need. It uses numbers: `resource.name[0]`, `resource.name[1]`.
- **`for_each`** → Use when each resource needs a **unique key/value**. It uses keys: `resource.name["dev"]`, `resource.name["prod"]`.
- **Easy rule:** `count = quantity` 📊, `for_each = named items` 🏷️.


 - **Using `count` — create 3 EC2 instances by number**

```
resource "aws_instance" "server" {
  count         = 3
  ami           = "ami-123"
  instance_type = "t2.micro"
}
```

 Terraform creates:

```
aws_instance.server[0]
aws_instance.server[1]
aws_instance.server[2]
```

 - **Using `for_each` — create instances with meaningful names**

```
resource "aws_instance" "server" {
  for_each = {
    dev  = "t2.micro"
    prod = "t2.small"
  }

  ami           = "ami-123"
  instance_type = each.value
}
```

 Terraform creates:

```
aws_instance.server["dev"]   → t2.micro
aws_instance.server["prod"]  → t2.small
```

 - **Key difference:** With `count`, Terraform identifies instances by **index** (`[0]`, `[1]`). With `for_each`, it identifies them by **key** (`["dev"]`, `["prod"]`). This matters when you add/remove items because `for_each` can track resources by their names/keys rather than shifting numeric indexes.
> Simple rule: If the collection can change and the items have meaningful identities/names, prefer for_each. count is better when the instances are genuinely interchangeable and their position doesn't matter.
```tf
for_each:
["web"] → web
["api"] → api
["db"]  → db

Remove api
       ↓
["web"] → web    ← unchanged
["db"]  → db     ← unchanged
["api"] → gone   ← only this is destroyed
```

```tf
count:
[0] → web
[1] → api
[2] → db

Remove api
       ↓
[0] → web
[1] → db    ← index changed so resource which were earlier pointing to api now point to db... drift detected.. terraform will destroy and re-create
[2] → gone
```

#### How can you conditionally create a resource in Terraform?
- Typically via count with a ternary expression: count = var.create_resource ? 1 : 0.
- If the condition is true, count = 1 and the resource is created; if false, count = 0 and it isn't created at all. for_each can achieve the same with a conditional empty map/set.
