- If a Terraform operation is interrupted (e.g., the process crashes or loses network connectivity) while holding a state lock, the lock may not be released automatically.

`terraform force-unlock <LOCK_ID>` manually releases the lock.

### Why remote state file:

- By default, resource attributes — including some sensitive values — are stored in plaintext inside the state file, which is a real security risk.
- Mitigations include:
  - Using a remote backend with encryption at rest.
  - Tightly restricting access to the backend via IAM policies.
  - For secrets used inside configuration, fetching them dynamically from a secrets manager. The values may still land in state, but they never need to be stored in source code.
- Marking variables with `sensitive = true` prevents their values from being echoed in CLI output and logs.

- If state manipulation is genuinely required, use the dedicated `terraform state` subcommands or `terraform import`, which perform the operations safely.

### DO Hands-on — Common causes of drift:

- Manual changes via the cloud console, often due to urgent hotfixes.
- Changes made by other automated tools that are not managed by Terraform.
- Failed or partially completed `terraform apply` runs.

- Drift is detected by running:

```bash
terraform plan
````

 - If Terraform proposes changes even though your configuration hasn't changed, the real infrastructure may have drifted from the recorded state.

 Remediation options:

 - Run `terraform apply` to revert the infrastructure back to what the code describes.
- Update the Terraform code to match the manual change.

 You can use:

```
terraform plan -refresh-only
```

- This updates the state to match reality without proposing infrastructure changes, allowing you to inspect drift before deciding how to act.

 ## Importing an existing resource:

 Write a Terraform resource block that matches the real resource, then run:

```
terraform import aws_instance.example i-1234567890abcdef0
```

 General syntax:

```
terraform import <resource_block> <cloud_resource_id>
```

- Alternatively, Terraform supports import blocks:

```
import {
  to = aws_instance.example
  id = "i-1234567890abcdef0"
}
```

- Terraform 1.5+ can also generate matching configuration for an imported resource:

```
terraform plan -generate-config-out=generated.tf
```

- The `removed` block lets you declare that Terraform should stop managing a resource — removing it from state — without destroying the underlying infrastructure:

```
removed {
  from = aws_instance.legacy

  lifecycle {
    destroy = false
  }
}
```

 ## If the Terraform state file is corrupted:

 - Restore the last known-good version from the state history.
- If using local state and the file is lost or corrupted with no backup, manually reconstruct the state by re-importing existing resources with `terraform import` or import blocks.
- Ensure your `.tf` files accurately describe the existing infrastructure.

 ## Variable values can be supplied using several methods.

 Command-line flags:

```
terraform apply -var="region=us-west-2"
```

 Variable definition files (`.tfvars`):

 - `terraform.tfvars` is loaded automatically.
- `*.auto.tfvars` files are loaded automatically.

 Environment variables:

```
export TF_VAR_region="us-west-2"
```

- Terraform automatically picks up variables using the `TF_VAR_` prefix.

- Outputs are the primary way to pass data between modules.

-  Setting `sensitive = true` on an output or variable block:

 - Suppresses the value from CLI output.
- Plan/apply logs display `(sensitive value)` instead.
- Helps prevent accidental display through `terraform output`, unless the value is explicitly requested by name or using an appropriate output option.

- Note: `sensitive = true` does **not** encrypt or remove the value from the Terraform state file. It primarily controls how Terraform displays the value.
